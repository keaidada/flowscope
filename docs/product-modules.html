面向「整个 SQL 项目」的血缘管理工具 —— 跨文件全局血缘、列级追踪、多视图可视化、本地 Rust 引擎。本文档按模块梳理现状,并标注每个模块的优化机会与优先级,供逐模块优化设计。

00

架构分层

monorepo 结构。前端通过 REST 连本地 Rust 后端(serve 模式);扩展形态另有 WASM 路径(serve 模式已弃用)。优化设计需理解数据在哪一层流动。

app/

React 前端。Chrome 扩展 + serve 模式。所有 UI 组件、hooks、lib(存储/适配器/缓存)。

packages/core

TS 分析封装层。analyzer.ts 统一入口,对接 WASM/REST。

packages/react

血缘可视化组件库。GraphView/MatrixView/SchemaView/HierarchyView 等可复用组件。

crates/core + export

Rust 分析引擎(全局/列级/lint/14 方言)+ 多格式导出。

crates/cli + wasm

cli = serve HTTP 后端(SQLite 持久化);wasm = 浏览器内分析(扩展用)。

02

分析与可视化核心

产品的灵魂。分析能力(引擎能算什么)+ 视图模式(怎么呈现)+ 可视化组件。这里是差异化竞争点,也是技术债集中区(双引擎、重复逻辑)。

A. 分析能力(引擎层)

🔁 单文件血缘

解析单个 SQL 出语句级血缘图(表/视图/CTE/列节点 + data_flow/ownership 边),识别 JOIN 与复杂度。

边界:13 方言 · 单文件 ≤10MB · current 模式仅分析当前文件。 · P2 10MB 截断 · P3 与多文件逻辑两套并存

🌐 多文件 / 全局血缘

合并多文件 AnalyzeResult,构建跨文件 globalLineage(节点去重、边合并),BFS 穿透临时表/CTE 建立物理表直接依赖。

边界:WASM 内存合并 + JS 表级精简 + 拓扑 DAG 层级。 · P1 大数据集 OOM · P1 跨语句穿透在前端 BFS 而非后端 SQL 计算

🎯 列级血缘

默认启用,产出 column 节点 + expression/ownership 边,支持列到列数据流追踪。

边界:GraphView 可 toggle · G6GraphView toggle 已加但列边渲染未完整接入 · 持久化到 SQLite columns 表。 · P0 G6 列边渲染未接入 · P2 G6GraphView 无 ColumnPanel 联动

📊 表级血缘

从 globalLineage 提取物理表(排除 CTE/临时/别名),BFS 建立表到表数据流。

边界:支持 Spark/Hive TEMP_*/TMP_* 过滤、USE database 推断。 · P3 extractSchemaFromResult 与 buildTableLevelLineage 两套重复逻辑并存

🧹 SQL Lint

Rust 内置规则集,产出 Issue(severity/span/autofix patch),支持 per-rule 配置与禁用。

边界:默认关闭,issues 面板开关激活 · 支持 autofix 直接修补。 · P2 默认关闭发现性差 · P2 规则文档/说明缺失

🧩 其他能力

Schema 解析与推断(resolvedSchema/PK/类型/temporary)· Hierarchy 层级树 · Pipeline 文件级 DAG 层级 · SQL 自动补全 · 语句分割 · 模板模式(Jinja-like)。

数据 · IO · 引擎

数据在哪、怎么进出、引擎能算什么。这是「能力上限」和「扩展性」的基础。

A. 存储机制

💾项目元数据 / 视图状态
功能
项目配置存 localStorage(flowscope-projects),视图状态按项目隔离存 Zustand persist(flowscope-view-states)。
优化机会
  • P2localStorage 5MB 上限,大项目元数据风险
🗄SQL 文件 / Schema / 缓存 / 血缘
功能
均经 REST 存后端 SQLite(project-files / schema-files / cache KV / lineage 三表 / table_metadata)。文件 500ms 防抖全量覆盖写。
优化机会
  • P1文件全量替换式写入,无增量更新,大项目保存慢
  • P1file-results batch save 逐行串行 POST,无批量接口
  • P2table_metadata 的 row_count/size_bytes 始终 -1(未采集)
⚡Backend 模式文件(内存)
功能
serve 模式 watch 的文件 → 内存虚拟项目 __backend__,只读不持久化。
优化机会
  • P0刷新即丢失选中态外的所有状态(不持久化)

B. 导入 / 导出 / 分享

📤导出(9 种格式)
功能
XLSX(多 sheet)/ CSV(zip 多文件)/ JSON / DuckDB SQL / Mermaid / HTML / PNG / SVG / PondPilot 跳转。
优化机会
  • P2XLSX 缺 Issues/ResolvedSchema sheet(仅 CSV/JSON 有)
  • P2CSV 必为 zip,无法单文件导出
  • P1PNG/SVG html-to-image 主线程阻塞,大图卡顿
  • P3DuckDB 仅 SQL 文本,无 .duckdb 二进制(WASM 限制)
🔗分享(URL 编解码)
功能
项目 gzip+base64url 编码到 #share= hash,可选文件/含 schema。
优化机会
  • P0serve 模式禁用分享(快捷键死路径)
  • P2纯客户端无短链,超大项目无法分享
  • P3仅 v1 payload,无版本迁移
🌊流式项目导出
功能
三步 session(start/add/finish)逐文件结果流式 merge → 统一导出,避免浏览器内存爆炸。
优化机会
  • P2无进度可视化(逐文件提交无反馈)
📥文件导入
优化机会
  • P2无 .zip 批量导入

🛠REST 端点(7 组)

04

跨模块全局问题(优化重点)

不是单个模块的问题,而是影响多个模块的系统性议题。优先解决这些,收益最大。

P0
serve 模式系统性隐藏前端功能
ProjectSelector(Static Files indicator)、ActivityBar Schema、SidebarSchema 编辑、GlobalDropZone、ShareDialog —— 一致性地把"纯前端能力"在连后端时禁用。根因:isBackendMode 在 UI 多处控制显隐。建议:统一决策 serve 模式该开放哪些前端能力,集中到一个策略层,而非散落判断。
P3
血缘图双引擎并存(React Flow + AntV G6)
GraphView(1101 行)与 G6GraphView(913 行)功能对齐但状态不共享,维护成本翻倍,列级血缘只在 RF 接入。建议:明确选型收敛到一个引擎(结合性能/交互/包体权衡),或明确分工(RF 交互探索 / G6 大图)。
P3
表级血缘两套重复逻辑
extractSchemaFromResult(AnalysisView)与 buildTableLevelLineage(merge-results.ts)并行存在。建议:合并为单一实现。
P1
大数据集性能(无虚拟化)
List/Matrix/Hierarchy/FileTree 全量渲染无虚拟滚动;全局血缘前端 BFS 而非后端 SQL 计算;布局计算大图延迟。建议:虚拟滚动 + 全局血缘下沉到后端 SQL。
P2
国际化不全
KeyboardShortcutsDialog 标题/分类、清理缓存文案等硬编码英文。建议:补全 i18n key + 加缺失文案校验。
P0
Backend 模式状态不持久化
serve 模式虚拟项目 __backend__ 在内存,刷新丢失选中态外所有状态。建议:至少持久化选中文件/展开节点/视图状态到后端或 localStorage。
